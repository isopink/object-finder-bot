## What `ObjectMemory` does

- `update_frame(observations, pose, in_view, t)`: decay every p to `t`, associate
  (Mahalanobis with item cov + observation cov `<= maha_thresh` and CLIP cosine
  `>= cos_thresh`, one-to-one, greedy by Mahalanobis distance), then
  - matched: Kalman update when `bearing is None`; otherwise an iterated EKF
    bearing update (10 re-linearizations max; plain EKF is `iters=1`) with
    `h(x) = atan2(y - vy, x - vx)` from `observation.view_pose`, std
    `sigma_bearing`; embedding running mean re-normalized; `n_obs`, `t_last = t`,
    `view_pose`, `label` updated; positive Bayes update;
  - unmatched memories with `in_view(item.mu, pose)` true: negative Bayes update;
  - unmatched observations: new memories with `p_init`.
- Time decay is lazy and tracked per item (`t_p`, the time its p was last decayed
  to), so an interval is never decayed twice. `query`, `update_frame`,
  `mark_found`, `mark_not_found` and `decay_to(t)` all go through it; going back
  in time does nothing.
- `query(text_embedding, t, k=None)`: `softmax(sim / T) * p` over all memories,
  top `k` (default `top_k`). Returns the live `MemoryItem` objects.
- `mark_found` / `mark_not_found`: positive / negative Bayes update (same `d`, `f`).
  Unknown ids are ignored.
- `save(path)` / `ObjectMemory.load(path, params)`: one `.npz` (no pickle), atomic
  replace, creates the folder; round trip keeps every field, `t_p` and the next id.
  Any path suffix works.
- Extras (not in `MemoryAPI`): `get(id)`, `remove(id)`, `decay_to(t)`, `add(obs)`,
  `associate(obs)`, `len(memory)`; module functions `kalman_update`,
  `bearing_update`, `bayes_positive`, `bayes_negative`, `time_decay`, `mahalanobis`.
- Thread-safe: one `RLock`, so the ROS observer and finder can share one instance
  in one process.
- p is clipped to `[1e-6, 1 - 1e-6]`.

## For the integrator

- Notes on behavior: time decay pulls a low-confidence memory (e.g. a moved
  object's old place) back toward 0.5 over `tau`; nothing is ever deleted
  automatically. Call `remove(id)` if pruning is wanted.
- The bearing EKF uses the robot position (`view_pose.x, view_pose.y`) as the ray
  origin, which matches `geometry.pixel_bearing` on `lane/2-geometry`.
