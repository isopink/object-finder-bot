## 1. 실습실 Wi-Fi에서 Claude Code 연결 실패

**증상**
- 노트북을 실습실 Wi-Fi(Jetson과 같은 네트워크)에 연결하면 Claude Code가 끊김.
- 터미널에서 실행하면 다음 오류가 남.
  ```
  API Error: Unable to connect to API: Self-signed certificate detected (SELF_SIGNED_CERT_IN_CHAIN)
  ```
- 학교 일반 Wi-Fi에서는 정상.

**원인 찾기**
1. 처음에는 실습실 Wi-Fi에 인터넷이 없다고 가정함. 그런데 11/18 로그에서 Jetson이 같은 네트워크에서 `apt`로 패키지를 받은 기록을 발견 → 인터넷은 되는 네트워크.
2. `Test-NetConnection <host> -Port 443`으로 github.com, claude.ai, api.anthropic.com 모두 **성공**.
   하지만 이 명령은 TCP 연결만 확인하고 인증서는 확인하지 않아서, 이 결과로는 원인을 가릴 수 없었음.
3. 오류 메시지가 가리키는 대로 인증서 발급자를 직접 확인.
   ```bash
   openssl s_client -connect api.anthropic.com:443 -servername api.anthropic.com -showcerts </dev/null \
     | grep -E "^ *[0-9] s:|i:"
   ```
   | 접속 대상 | 학교 일반 Wi-Fi | 실습실 Wi-Fi |
   |---|---|---|
   | api.anthropic.com | Google Trust Services (정상) | **학교 보안 장비(eWalker)가 발급** |
   | github.com | Sectigo (정상) | Sectigo (정상) |
4. 결론: 학교의 HTTPS 검사(SSL 인스펙션) 장비가 **Anthropic 쪽 통신만 골라서** 중간에서 인증서를 바꿔 끼움.
   Claude Code(Node.js)는 그 인증서를 모르므로 연결을 거부함. github는 검사 대상이 아니라 git은 영향이 없음.

**해결**
- 보안 장비의 **루트 인증서만** 파일로 저장. 처음 저장한 체인에는 api.anthropic.com용 위조 인증서도 섞여 있어서 루트 하나만 남김.
- 시스템 전체가 아니라 Node.js 프로그램만 이 인증서를 믿도록 설정.
  ```powershell
  setx NODE_EXTRA_CA_CERTS "$env:USERPROFILE\lab-ca.pem"
  ```
- 되돌리기: `setx NODE_EXTRA_CA_CERTS ""`

**배운 점**
- "포트 연결 성공"과 "통신 성공"은 다르다. TLS 문제는 `openssl s_client`로 인증서 체인을 직접 봐야 보인다.
- 정상 네트워크의 결과를 먼저 찍어 두면, 문제 네트워크의 결과와 바로 비교할 수 있다.
- 사설 인증서를 신뢰시키면 그 장비가 통신 내용을 볼 수 있다. 그래서 출처(학교 공식 장비인지)를 확인하고, 적용 범위를 Node.js로 좁혔다.
- 시행착오: 한 번은 학교 일반 Wi-Fi에 연결된 상태에서 테스트해 놓고 실습실 결과로 착각했다. 이후 테스트 스크립트 첫 줄에 **현재 SSID를 출력**하도록 했다.

## 2. 설정 후에도 Orca 안에서만 실패

**증상**
- 1번 설정 후, 새로 연 일반 PowerShell에서는 Claude Code가 접속됨.
- Orca(터미널 관리 앱)를 껐다 켜도 Orca 안에서는 계속 실패.

**원인 찾기**
- Orca 터미널 안에서 `$env:NODE_EXTRA_CA_CERTS`를 확인하니 **비어 있음**. 사용자 환경 변수에는 값이 있었음.
- Orca 프로세스 시작 시각을 보니, 창은 새로 떴지만 **백그라운드 데몬은 `setx` 이전부터 계속 실행 중**이었음.
- Orca 터미널은 데몬이 만들기 때문에 데몬의 예전 환경 변수를 물려받음.

**해결**
- Orca를 닫은 뒤 남은 프로세스까지 모두 종료하고 다시 실행.
  ```powershell
  Get-Process Orca -ErrorAction SilentlyContinue | Stop-Process -Force
  ```
- 재실행 후 Orca 안에서도 환경 변수가 보이고 실습실 Wi-Fi에서 Claude Code가 동작함.

**배운 점**
- Windows 환경 변수(`setx`)는 **새로 시작한 프로세스부터** 적용된다. 창을 다시 여는 것과 프로세스를 다시 시작하는 것은 다르다.
- "A에서는 되고 B에서는 안 된다"면 두 환경의 변수 값을 직접 출력해서 비교하는 것이 가장 빠르다.

## 3. 우회 시도: 아이폰 USB 테더링 (포기)

**시도한 이유**
1번의 원인을 찾기 전, 인터넷은 휴대폰으로 쓰고 Jetson 접속만 실습실 Wi-Fi로 하는 구성을 시도함.

**진행**
- 노트북이 아이폰을 정상 인식(`Apple iPhone`, `Apple Mobile Device Ethernet` 드라이버 OK)하는 것까지 확인. 케이블 문제가 아님.
- 테더링 어댑터가 계속 `Disconnected`. 요금제상 개인용 핫스팟을 쓸 수 없어서 중단.

**배운 점**
- 우회책보다 원인을 먼저 찾는 게 나았다. 원인(1번)을 알고 나니 테더링 자체가 필요 없었다.
- 필요하면 쓸 수 있는 대안: USB Wi-Fi 동글로 두 네트워크에 동시 연결하고, 인터페이스 우선순위(`InterfaceMetric`)로 경로를 나누는 방법.

## 4. NetClient5 설치 중 드라이버 차단 경고

**증상**
학교 PC 관리 프로그램(NetClient5)을 설치하는 중 Windows 경고가 뜸.
```
이 장치에 드라이버를 로드할 수 없습니다. 드라이버: cpuz139_x64.sys
보안 설정에서 이 드라이버를 취약한 드라이버로 감지하여 로드하지 못하도록 차단하고 있습니다.
```

**원인 찾기**
- 다운로드 폴더와 실행 중인 프로세스로 어느 설치 파일이 원인인지 확인 (NetClient5).
- 막힌 건 하드웨어 정보 수집용 구버전 CPU-Z 드라이버. Windows 11의 "취약한 드라이버 차단 목록"에 올라 있음.
- 설치 로그를 보니 에이전트 서비스는 실행 중이고 학교 서버로 상태 보고도 성공.

**해결**
- 경고만 닫음. 보안 설정(메모리 무결성 / 취약한 드라이버 차단)은 **끄지 않음**.
- 프로그램의 핵심 기능은 정상 동작. 하드웨어 사양 보고만 빠짐.

**배운 점**
- 경고 창이 떴다고 설치가 실패한 것은 아니다. 실제로 무엇이 막혔는지(로그, 서비스 상태)를 확인하고 판단한다.
- 보안 기능을 끄는 것은 마지막 수단이다.

## 5. 실습실 Wi-Fi에서 Jetson SSH 응답 없음

**증상**
- 노트북은 실습실 네트워크에 정상 연결(`192.168.1.x`, 게이트웨이 `192.168.1.1`).
- `ssh` 설정의 Jetson 주소(`192.168.1.206`) 22번 포트가 응답 없음.
  ```
  ssh: connect to host 192.168.1.206 port 22: Connection timed out
  ```

**확인한 것**
- 학교 일반 Wi-Fi에서 같은 주소로 접속하면 TCP는 열리는데 SSH 응답이 없음 → 다른 네트워크의 다른 장비. 그 Wi-Fi로는 Jetson에 닿지 않음.

- 실습실 네트워크 전체(`192.168.1.2~254`)에서 22번 포트가 열린 기기를 찾았는데 **하나도 없음** → IP가 바뀐 게 아니라 Jetson이 네트워크에 없음.

**원인**
두 가지가 겹쳐 있었음.
1. **Jetson이 꺼져 있었음.** ASUS PE1000N은 처음 써 보는 장비라 전원 켜는 법부터 찾아야 했음. 같은 계열(PE100A, PE400D) 설명서를 보고 앞면 전원 버튼을 찾아 켬.
2. **노트북 Wi-Fi가 몰래 바뀌어 있었음.** 다시 스캔하자 254개 주소가 **전부** 열린 것으로 나옴. 이상해서 네트워크를 확인하니 Windows가 학교 일반 Wi-Fi로 자동으로 옮겨 가 있었음. 그 네트워크의 보안 장비가 모든 연결에 대신 응답해서, 열린 것처럼 보인 것.

**해결**
- 실습실 Wi-Fi에 다시 연결하고, 학교 일반 Wi-Fi의 "자동으로 연결"을 해제.
- Jetson이 켜진 뒤 `ssh` 접속 성공 (비밀번호 요구 = SSH 서버 응답).
- 이후 매번 비밀번호를 치지 않도록 SSH 키(ed25519)를 만들어 Jetson `~/.ssh/authorized_keys`에 등록.
  ```powershell
  ssh-keygen -t ed25519 -f "$env:USERPROFILE\.ssh\id_ed25519"
  type "$env:USERPROFILE\.ssh\id_ed25519.pub" | ssh device06@<jetson-ip> "mkdir -p ~/.ssh && chmod 700 ~/.ssh && cat >> ~/.ssh/authorized_keys && chmod 600 ~/.ssh/authorized_keys"
  ```
- `sudo`는 여전히 비밀번호가 필요하므로 udev 규칙 설치처럼 `sudo`가 필요한 명령은 직접 터미널에서 실행.

**배운 점**
- "전부 열림"은 "전부 닫힘"만큼 이상한 결과다. 결과가 너무 좋으면 측정 환경(지금 어느 네트워크인지)부터 의심한다. 1번의 교훈(테스트 전에 SSID 확인)을 여기서도 지켰어야 했다.
- 포트 스캔으로 "열림"이 나와도, 실제로 `ssh`를 붙여서 배너가 오는지 확인해야 진짜 SSH 서버다.
- 원격 장비 문제를 볼 때는 **전원 → 네트워크 → 서비스** 순서로 아래층부터 확인한다.

## 6. D455용 librealsense 빌드 실패 (cmake 2번)

**증상**
`./robot/install_realsense_jetson.sh`가 시작 1분 만에 `[FAIL] cmake failed`로 끝남. 고친 뒤 다시 돌리자 다른 오류로 또 실패.

**원인 찾기 1: CMake 버전**
```
Compatibility with CMake < 3.5 has been removed from CMake.
```
- 시스템 cmake는 3.16인데 오류는 CMake 4.x의 메시지. `which -a cmake`로는 시스템 것만 보였음.
- 스크립트는 conda 환경을 켠 뒤 cmake를 부름 → conda 환경 안을 보니 **pip로 설치된 CMake 4.4**가 있었음. 이 버전이 librealsense의 오래된 설정을 거부.
- 해결: 스크립트가 `/usr/bin/cmake`를 직접 쓰도록 수정.

**원인 찾기 2: Python을 못 찾음**
```
Could NOT find Python (missing: Python_INCLUDE_DIRS Development) (found version "2.7.18")
```
- conda Python(3.8)을 넘겼는데 cmake는 시스템 Python 2.7을 찾고 있었음.
- 스크립트는 `PYTHON_EXECUTABLE`(옛 방식)만 넘기는데, librealsense는 새 방식(`FindPython`)을 써서 `Python_EXECUTABLE`(대소문자가 다름)을 읽음.
- 해결: `-DPython_EXECUTABLE`도 넘기도록 수정. 스크립트 전체를 다시 돌리기 전에 cmake만 따로 실행해 통과를 확인.

**덤: 빌드 폴더 오염**
도중에 Jetson이 꺼지면서(7번) cmake가 받다 만 파일이 남아 `nlohmann_json` 업데이트 오류가 남. 빌드 폴더를 지우고 다시 실행해서 해결.

**설치 단계에서 2번 더**
- `sudo make install`이 conda 환경 안에 `pyrealsense2` 폴더를 **root 소유로** 만들어서, 스크립트가 그 안에 모듈을 복사하지 못함(`Permission denied`). → 폴더가 root 소유면 소유권을 가져오도록 수정.
- 다시 돌렸더니 이번에는 `[OK] all checks passed`가 나왔는데 실제로는 설치가 안 된 상태였음. 폴더에 보조 파일만 있어도 `import pyrealsense2`가 성공해서(빈 namespace 패키지), 스크립트가 "이미 설치됨"으로 판단하고 복사를 건너뜀. 버전이 `?`로 나온 게 단서. → `rs.context`까지 있는지 확인하도록 수정.

**속도**
Jetson 전원 모드가 `MODE_15W_2CORE`(코어 2개)였음. `sudo nvpmodel -m 8`(20 W, 6코어)로 바꾼 뒤 `make -j6`.

**배운 점**
- 오류 메시지가 가리키는 버전과 실제로 설치된 버전이 다르면 **PATH**를 의심한다. 가상환경(conda)을 켜면 같은 이름의 다른 프로그램이 앞에 온다.
- CMake 변수는 대소문자를 구분한다. `PYTHON_EXECUTABLE`과 `Python_EXECUTABLE`은 다른 변수다.
- 긴 빌드 스크립트를 처음부터 다시 돌리기 전에, 실패한 단계만 손으로 재현해서 고쳐졌는지 먼저 확인하면 시간을 아낀다.
- `sudo`로 만든 파일은 root 소유가 된다. 일반 사용자 폴더(conda 환경) 안에서 `sudo make install`을 하면 권한이 섞인다.
- "OK"가 나와도 검사가 무엇을 확인했는지 봐야 한다. import 성공은 모듈이 **쓸 수 있다**는 뜻이 아니다.

## 7. 작업 중 Jetson이 갑자기 꺼짐 + 노트북 Wi-Fi 다시 바뀜

**증상**
cmake 시험 중에 SSH가 끊김. 노트북은 학교 Wi-Fi로 또 넘어가 있었고, 실습실 Wi-Fi로 돌아온 뒤에도 Jetson이 응답하지 않음.

**배운 점**

## 8. 로봇 배터리 0.05 V, 충전 안 됨 (진행 중)

**증상**
bringup은 성공(`Run!`)하는데 `/battery_state` 전압이 0.05 V. 11/18과 같은 증상.

**원인 찾기**
- OpenCR는 Jetson USB 전원만으로도 켜지기 때문에 bringup은 배터리 없이도 성공한다. "bringup 성공 = 전원 정상"이 아님.
- LiDAR가 빠져 bringup이 거부될 때는 OpenCR 노드(`turtlebot3_ros`)만 따로 띄워 전압을 읽었음.
- 배터리는 충전기에 꽂혀 있는 상태였음 → 로봇에는 배터리가 없는 상태라 0 V가 정상.

- 충전기에 꽂자 **빨간불이 깜빡임**. 충전기 라벨: "red flash = output short-circuit or wrong polarity".
- 극성과 연결을 확인하고 **다른 충전기로 바꿔도 같은 증상** → 충전기 문제가 아니라 배터리 쪽.
- 11/18에도 로봇에 꽂은 상태로 0.07 V였음 → **과방전**으로 배터리 전압이 0 V 근처라 충전기가 단락으로 판단한 것으로 추정. 배터리 커넥터나 선의 단락일 가능성도 남아 있음.

**판단**
과방전된 Li-Po를 억지로 충전하면 부풀거나 불이 날 수 있음. 직접 살리지 않고 조교님께 교체를 요청하기로 함.

**임시 대책: 보조배터리로 OpenCR 전원 공급 (계획, 아직 검증 안 함)**
교체를 기다리는 동안 보조배터리(아트뮤 PB220, USB-C PD, C포트 최대 75 W, 출력표에 12V 3A 있음)로 OpenCR에 전원을 주기로 함.

- 보조배터리의 일반 USB 5V로는 안 됨. OpenCR의 USB 5V는 보드(MCU)만 켜고, 모터(Dynamixel) 포트와 `/battery_state` 전압 측정은 배터리 입력(VIN)에서만 나옴.
- 바퀴 모터(XL430)는 최대 12V → PD 트리거 케이블은 반드시 **12V 고정**. 15V나 20V는 금지.
- 배터리 커넥터는 T형(딘스). 바로 옆에 있는 OpenCR **DC 잭**(12V 어댑터 입력, 같은 VIN 라인)을 쓰기로 함. 납땜이나 커넥터 작업이 필요 없음.
- 필요한 케이블: USB-C PD 트리거 12V → DC 5.5×2.1 mm(중심 +). 구멍 규격(2.1 mm인지 2.5 mm인지)은 사기 전에 확인한다.

```
PB220 (USB-C) ──[PD 트리거 12V, DC 플러그]──> OpenCR DC 잭
Jetson ──USB──> OpenCR   (통신, 그대로)
Jetson ──> 벽 어댑터     (실습실 작업 중)
```

연결 순서:
1. 죽은 Li-Po를 분리한다. 두 전원을 동시에 꽂지 않는다.
2. 멀티미터로 트리거 케이블 출력이 12V인지, 중심이 +인지 확인한다.
3. OpenCR 전원 스위치를 끈 상태에서 DC 잭에 꽂고, 스위치를 켠다.
4. `ros2 topic echo /battery_state --once`로 12V 근처가 나오는지 보고, teleop으로 바퀴가 도는지 확인한다.

**데모 때 전원 계획**
데모에서는 Jetson 벽 어댑터(ASUS/Delta ADP-65DE B, 19.0V 3.42A 65 W)를 쓸 수 없음. 전원을 두 개로 나눈다.

| 대상 | 전원 | 케이블 |
|---|---|---|
| OpenCR / 모터 | 교체 받은 Li-Po, 또는 12V를 지원하는 보조배터리 한 대 더 | 12V 트리거 → DC 잭 |
| Jetson (Xavier NX, PE1000N) | PB220 | PD 트리거 **20V** → 어댑터와 같은 DC 플러그 (보통 5.5×2.5 mm, 중심 +, 실측 필요) |

- 젯슨에 20V를 주기 전에 PE1000N 본체 라벨의 입력 범위에 20V가 들어가는지 확인한다.
- 12V 3A(36 W)로 젯슨을 돌리는 것은 원래 어댑터(65 W)보다 한참 작아서 RealSense와 Nav2를 함께 켜면 빠듯함 → 20V를 쓴다.
- PB220 한 대로 두 곳에 동시에 공급하지 않는다. 포트를 여러 개 쓰면 출력이 나뉘거나 전압이 내려갈 수 있고, 모터가 순간적으로 전류를 끌어갈 때 젯슨이 재부팅될 수 있음 (7번 참고).
- 데모 전에 보조배터리 전원으로 데모 시나리오 전체를 한 번 끝까지 돌려 보고, 보조배터리와 선은 로봇 위에 케이블타이로 고정한다.

**추가 진행 (11/20 밤)**
- 새로 찾은 커넥터로 충전한 뒤 로봇에 꽂자 `/battery_state`가 **12.02 V**로 나옴. 그런데 바퀴가 안 돎.
- 한 프로그램 안에서 `/cmd_vel`을 보내며 `/joint_states`를 읽으니 바퀴 위치·속도가 **정확히 0.0**에서 안 바뀜 → OpenCR가 바퀴 모터(Dynamixel)와 통신을 못 함. OpenCR 자체 버튼(SW1/SW2) 시험에서도 안 돎 → ROS 문제가 아님.
- 모터 선을 다시 꽂고 OpenCR를 껐다 켜자 바퀴 위치가 **실제 값**(3.66, 5.92)으로 나옴 → 선 접촉 문제였음.
- 하지만 모터 전원 켜기(`/motor_power`)가 `Failed transmit instruction packet`으로 실패하고, 전압이 **11.19 V → 0.31 V**로 급락. 배터리가 덜 충전돼 부하에서 전압이 무너지고 OpenCR가 재시작된 것으로 추정. 충분히 충전한 뒤 다시 시험하기로 함.
- 덤: OpenCR가 재시작되면 USB 포트 이름이 `/dev/ttyACM0` → `/dev/ttyACM1`로 바뀜. 노드는 `/dev/opencr`(udev 심볼릭 링크)로 열어야 따라간다.

**배운 점**
- "전원 정상 + 명령 전달 정상 + 그래도 안 움직임"이면 센서 값(`/joint_states`)이 정확히 0인지 본다. 정확히 0은 "멈춤"이 아니라 "통신 없음"일 때가 많다.
- 같은 증상이 장비를 바꿔도 반복되면, 바꾸지 않은 쪽이 원인이다 (충전기 2대 → 배터리).
- Li-Po는 다 쓴 뒤 방치하면 과방전으로 못 쓰게 된다. 실습이 끝나면 배터리를 분리하고, 다음 실습 전에 충전해 둔다.
- 로봇은 역할별로 전원이 나뉜다. Jetson은 판단(센서 처리, SLAM, Nav2)을 하고 USB로 `/cmd_vel`을 보낸다. OpenCR은 실행(모터, 오도메트리, IMU, 전압 측정)을 맡는다. USB로 OpenCR이 켜지는 것과 모터에 전원이 들어가는 것은 별개다.
- USB-C PD 보조배터리는 트리거 케이블로 원하는 고정 전압을 뽑을 수 있다. 다만 PD에서 12V는 선택 사항이라 출력표를 먼저 확인해야 하고, 받는 쪽 최대 전압(모터 12V)을 넘기지 않아야 한다.

## 10. 노트북 음성 프로그램 설치·모델 다운로드 실패 (11/24)

**증상**
`음성질문.cmd`로 설치하면 Whisper 모델을 못 받는다.
```
CERTIFICATE_VERIFY_FAILED: self-signed certificate in certificate chain
```

**원인 찾기 (4겹)**
1. 노트북의 기본 Python이 3.14인데 faster-whisper 계열 패키지는 이 버전용 바퀴(wheel)가 없을 수 있음 → 3.12 가상환경으로 해결.
2. 프로그램에는 실습실 인증서(`lab-ca.pem`)를 쓰는 코드가 있는데, 그 코드가 `certifi`를 가져오지 못하면 **아무 말 없이 건너뜀**. 가상환경에 `certifi`가 없었다.
3. `certifi`를 깔아도 실패 → 환경변수 `SSL_CERT_FILE`이 이미 conda의 인증서 파일로 설정돼 있었고, 코드가 "이미 있으면 유지"(`setdefault`)였다 → 강제로 덮어쓰도록 수정.
4. 그래도 파일 다운로드에서 실패 → Hugging Face의 Rust 다운로더(Xet)는 이 환경변수를 무시한다 → `HF_HUB_DISABLE_XET=1`로 일반 다운로드 사용.
- 인증서가 맞는지는 `openssl s_client`로 huggingface.co의 체인을 보고(발급자가 학교 보안 장비) `lab-ca.pem`과 같은지 확인했다. 11/20 트러블슈팅 1번에서 쓴 방법과 같다.

**해결**
위 4가지를 `scripts/laptop_voice/`에 반영. 모델을 받은 뒤 TTS로 만든 "Where is the banana?"를 3번 인식시켜 모두 정확, 약 2.5초(노트북 CPU, `base.en`).

**덤: 질문 전달 12초 → 5초**
SSH로 `ros2 topic pub --once`를 부르면 환경 설정(3.3초)과 명령 시작(4.9초)이 겹쳐 약 12초가 걸렸다. 구독자를 기다렸다가 한 번 발행하는 작은 rclpy 스크립트로 바꿔 약 5초가 됐고, 아무도 듣고 있지 않으면 그렇게 알려 준다.

**배운 점**
- 환경변수를 "없을 때만 설정"하면 다른 도구가 먼저 넣어 둔 값에 진다. 인증서처럼 틀리면 안 되는 값은 덮어쓴다.
- 조용히 `return`하는 예외 처리는 원인을 숨긴다. 최소한 경고를 출력한다.
- 문제가 겹쳐 있으면 하나 고칠 때마다 같은 오류 메시지가 그대로 나올 수 있다. 메시지가 같아도 원인은 바뀐 것일 수 있으니 매번 환경(환경변수, 설치 목록)을 직접 출력해 본다.

## 11. NanoOWL worker가 간헐적으로 500 (11/24)

**증상**
Jetson에서 NanoOWL worker는 40초 만에 떴는데(`/health`는 정상) 사진을 보내면 매번 서버 오류.
```
HTTP 500 {"error": "AttributeError: 'NoneType' object has no attribute 'get_binding_index'"}
```
같은 코드로 4번 시험해서 3번 실패, 1번 성공.

**원인 찾기**
- worker 로그에 `TRT ... Cuda Runtime (out of memory)`, `NvMapMemAllocInternalTagged ... error 12` → TensorRT 실행 문맥이 만들어지지 않아 `None`. 11/18에도 같은 계열의 `NvMapMemAllocInternalTagged` 오류가 있었다.
- 그런데 `free -m`의 `available`은 2 GB로 충분해 보였다. `/proc/meminfo`를 보니 `MemFree`는 약 0.15 GB, `Cached`는 약 2.4 GB. Jetson의 GPU 메모리는 **파일 캐시를 쓰지 못해서** `available`을 믿으면 안 된다.
- Jetson을 1시간 넘게 켜 두며 파일을 많이 읽어 캐시가 쌓인 상태였다. 재부팅 직후에는 문제가 없었을 것이다(동하 님은 성공).

**해결**
`sudo` 없이 캐시를 비우는 `robot/lib/drop_cache.py`를 만들었다(`posix_fadvise(DONTNEED)`, 읽기 전용 파일의 깨끗한 캐시만 버림). 31초에 1.4 GB 확보. `worker.sh`가 worker 시작 전에 자동 실행. 이후 연속 4번 성공.

**남은 것**
처음 3번의 실패 중 하나는 캐시를 비운 직후(MemFree 4.1 GB)에도 났다. 그래서 원인이 캐시만은 아닐 수 있다. 시연 전 전체 실행에서 계속 확인하고, 실패하면 worker를 다시 시작한다.

**배운 점**
- 통합 메모리를 쓰는 보드(Jetson)에서는 `free`의 `available`이 GPU가 쓸 수 있는 양이 아니다. `MemFree`와 캐시를 같이 본다.
- 서버가 "살아 있다(/health)"와 "일을 한다(/detect_embed)"는 다르다. 시험은 실제 요청으로 한다.
- 같은 시험을 한 번만 하고 성공/실패를 판단하지 않는다. 반복해서 비율을 본다.

## 13. OpenCR가 모터를 못 찾음 + Jetson 반복 재부팅 (11/25)

**증상**
- bringup은 성공(`Run!`), 배터리 12.4 V, 노드 오류 없음. 그런데 바퀴가 안 돌고 `/joint_states`의 바퀴 위치가 **처음부터 끝까지 정확히 0.0**.

**원인 찾기**
- 03:30에 모터 선을 다시 꽂고 OpenCR 스위치를 껐다 켜자 위치가 실제 값(2.73, 5.88)으로 나오고 제자리 3초 회전 성공. 그런데 재부팅 뒤 다시 0.0.

- Jetson 재부팅: 커널 로그에 USB 장치 이상은 없고, 정상 종료 기록이 없어 **전원이 순간 끊긴 것**으로 보임. 전원 선이 바닥에 늘어져 있었음. 확정은 못 함.

**해결**
1. OpenCR USB 뽑기 → 스위치 OFF 5초 → ON(도레미 확인) → USB 연결
2. bringup 재시작 (포트는 `/dev/opencr`, 이제 `env.sh` 기본값)
3. Jetson 전원 선은 판에 케이블타이로 고정

**배운 점**
- `/joint_states`가 "0"이 아니라 **정확히 0.0**이면 통신이 없는 것이다 (멈춘 것과 구별).
- USB로도 전원을 받는 보드는 스위치로 껐다 켜도 리셋되지 않을 수 있다. 시작음이 나는지로 리셋 여부를 확인한다.
- 장치가 다시 꽂히면 이름이 바뀐다. 고정 이름(`ttyACM0`) 대신 udev 링크를 쓴다.

## 14. ROS 노드끼리 서로 못 들음 (`/dev/shm` 찌꺼기, 11/25)

**증상**
- bringup 프로세스는 살아 있고 `Run!`도 찍혔는데 `ros2 topic hz /odom`이 "not published yet". 시험 스크립트가 값을 **하나도** 못 받음. 한 번은 로봇이 움직였는지조차 알 수 없었다(피드백이 없어서).

**원인 찾기**
- `/dev/shm`에 Fast DDS 공유 메모리 파일(`fastrtps_*`)이 **30~46개** 남아 있었다. 노드를 여러 번 켜고 끄는 사이에 쌓임. 같은 PC 안(`ROS_LOCALHOST_ONLY=1`)에서는 이 공유 메모리로 통신하므로 찌꺼기가 있으면 서로를 못 찾는다.
- 파일을 지우고 `ros2 daemon stop` 후 bringup을 다시 띄우자 `/odom` 121개/6초(약 20 Hz).

**해결**
`bringup.sh`가 시작 전에 이 파일을 지운다(내 ROS 프로세스가 하나도 없을 때만).

**배운 점**
- "프로세스 살아 있음" ≠ "통신됨". 수신 쪽에서 직접 메시지를 세어 본다.
- 움직이는 시험 스크립트는 **피드백이 없으면 출발하지 않게** 만든다. 처음 버전은 피드백이 없어도 30초 동안 명령을 계속 보냈다.

## 17. 파이 카메라(v2)로 교체 시도 (11/25)

**동기**: C920(약 160 g)이 기둥 위에서 흔들림. 파이 카메라는 약 3 g.

**배운 점**
- 필요한 도구(SD 리더, USB 메모리, micro-HDMI 선)는 시작 전에 목록으로 확인한다.
- 네트워크 보안 장비는 "된다/안 된다"가 사이트마다 다르다. 필요한 주소 몇 개를 `openssl s_client`로 먼저 확인하면 헛걸음을 줄인다.

## 18. 회전이 `/odom`에 안 남아서 ㄱ자 지도가 일자로 나옴 (11/25 오후)

**증상**
- ㄱ자로 운전했는데 SLAM 지도는 긴 일자 통로. 출발점으로 돌아왔는데 기록상 위치는 10 m 밖.
- `/imu`, `/joint_states`는 정상으로 나오고, **직진은 `/odom`에 정확히 남는데**(바퀴 0.16 m → odom 0.161 m) **회전만 0**.

**원인 찾기**
같은 회전을 세 값으로 동시에 쟀다 (`/odom`, `/imu`, `/joint_states`로 계산한 바퀴 방향).

| 회전 | 바퀴 방향 | `/imu` 방향 | `/odom` 방향 |
|---|---|---|---|
| 키보드로 제자리 약 90° | +97.7° | +91.7° | **0°** |

- `waffle_pi.yaml`의 `diff_drive_controller: odometry: use_imu: true` → 방향을 IMU로 계산한다. 센서는 살아 있는데 계산 쪽에 IMU 값이 안 들어가는 것으로 보인다. 같은 날 오전과 15:05에는 정상(84.5°)이었다가 다시 0이 되는 등 **간헐적**이다.
- `-p odometry.use_imu:=false`를 명령줄에 붙여도 **효과 없음**: 파일의 노드별 설정이 이긴다 (`ros2 param get /diff_drive_controller odometry.use_imu` → True).
- 파일 사본에서 `use_imu: false`로 바꿔 `--params-file`로 주자 `ros2 param get` → False, 회전 **+91.6° = 바퀴 +91.6°**.

**대책**
`OFB_ODOM_IMU=0 ./robot/bringup.sh` → `robot_ld08.launch.py`가 `/tmp`에 `use_imu: false` 사본을 만들어 쓴다 (기본값 1은 이전과 같음). `start_all.sh`도 이 변수를 넘긴다.

**남은 것**
- 사본 설정으로 켠 다음 세션에서도 지도가 안 꺾였다는 보고가 있었다 (16:18). 그 회전은 Jetson이 다시 꺼져 기록을 못 봤다. **다음 실습에서 `live_map.py`를 보며 다시 확인**할 것.
- IMU 쪽이 왜 간헐적인지는 모름 (19, 20번과 관련 있을 수 있음).

**배운 점**
- "지도가 이상하다"면 SLAM보다 먼저 odom이 회전을 따라가는지 본다: 제자리 90° 돌리고 `/odom`과 바퀴 값을 비교.
- ROS 2 파라미터는 명령줄 `-p`보다 파일의 노드별 값이 우선할 수 있다. 바꾼 뒤 `ros2 param get`으로 확인한다.

## 19. Jetson 재부팅 직후 시계가 뒤로 맞춰짐 (11/25)

**증상**: 재부팅 후 바로 켠 `turtlebot3_node`가 "Start Calibration of Gyro"에서 2분 가까이 멈춤, SLAM 로그에 `Message Filter dropping message`.

**대책**: 재부팅 뒤 `timedatectl`에서 `System clock synchronized: yes`를 보고, 1~2분 뒤에 ROS를 켠다.

## 20. 확인용 ROS 명령을 자주 켰다 끄면 노드끼리 또 못 들음 (11/25)

**증상**: 14번을 정리한 뒤에도 몇 분 만에 `/dev/shm`의 Fast DDS 파일이 0 → 48~64개, 새 노드(SLAM, teleop의 `/odom` 검사, 시험 스크립트)가 기존 노드를 못 찾음. SLAM이 시작 직후 `karto::Exception`/세그폴트로 두 번 죽음.

**대책**: 확인은 가능한 한 로그 파일로 한다. 꼬이면 전부 끄고(`_ros2_daemon` 포함) `/dev/shm/fastrtps_*`를 지운 뒤 **필요한 노드를 한꺼번에** 다시 켠다. 그렇게 켠 SLAM은 살아 있었다.

## 23. 나중에 켠 노드가 `/odom`, `/map`을 못 찾음 (11/27)

## 26. 지도가 실제 갈 수 있는 곳보다 넓음 (11/27)

**한계**: 지도를 그릴 때 지나간 통로 안에서만 다닌다. 다른 곳을 쓰려면 그곳도 한 번 지나간다.

## 27. 지도가 직선으로 뭉개지거나 벽이 겹침: LiDAR가 180° 반대로 달려 있었음 (11/27 저녁)

**증상**: SLAM 지도가 한 줄로 뭉개지고, 실시간 지도의 로봇 화살표가 몸체 뒤쪽을 가리킴.
**확인**: 카메라 쪽(`w`로 가는 방향) 0.44 m 앞에 물체를 두니 `/scan`에서 **185°**에 보였다. 0.05 m/s로 10.7 cm 전진(odom)시키자 그 물체가 10.5 cm **가까워졌고** 0° 쪽 거리는 1.07 → 1.14 m로 늘었다. LiDAR의 0°가 로봇 뒤를 보고 있었다.
**원인**: LiDAR가 판 위에 반대로 조립됨. 바퀴 기록은 "앞으로", 스캔 맞춤은 "뒤로"라고 해서 SLAM이 무너졌다. 11/25, 11/27 낮의 지도(`room_l3` 등)는 전부 이 상태로 만든 것.
**해결**: `scan_filter.py --rotate-deg` (`OFB_SCAN_ROTATE_DEG`, 이 로봇 기본 180). 빔 배열을 반 바퀴 밀어서 내보낸다. 적용 후 같은 물체가 0° 근처 0.33 m에 보임. LiDAR를 바로 달면 0으로.
**교훈**: 센서를 단 뒤 "앞에 물체 → 몇 도에 보이나"를 30초만 확인하면 됐다. 지도가 이상할 때 알고리즘보다 장착 방향을 먼저 본다.

## 28. 방향 수정 뒤에도 지도가 15 m로 커지고 벽이 틀어짐: `/odom`이 멈춰 있었음 (11/27 저녁)

## 31. 워커를 다시 켜면 TensorRT 엔진이 메모리를 못 받음 (11/27 밤)

**증상**: 부팅 후 첫 실행은 되는데, `stop_all.sh` 뒤 다시 켜면 `Cuda Runtime (out of memory)` → `Engine deserialization failed` → 워커가 자체 점검에서 종료. 두 번 연속. 시작 전 `drop_cache.py`로 MemFree를 4.1 GB까지 만들어도 같았다. 재부팅하면 됨.
**분석**: 워커는 약 4.65 GB(RSS)를 쓴다. 부팅 직후에는 MemFree 5.5 GB라 간신히 들어간다. 한 번 돌린 뒤에는 아무것도 안 켜져 있어도 "used"가 638 → 1550 MB로 남아(프로세스 RSS 합으로는 설명 안 되는 약 0.9 GB, GPU 드라이버 쪽으로 추정) MemFree가 4.1 GB에 그친다. 여기에 CLIP(577 MB), OWL-ViT(584 MB), 엔진(184 MB) 파일을 읽으며 생기는 **페이지 캐시 1.3 GB**가 겹치면, 마지막 순서인 엔진 로드 때 빈 메모리가 없다. Jetson의 GPU 할당기는 페이지 캐시를 못 쓴다(11번).
**해결**: `scripts/vision_worker.py`의 `CacheDropper`. 모델을 읽는 동안 1.5초마다 가중치 파일들의 캐시를 `posix_fadvise(DONTNEED)`로 버린다(이미 RAM/GPU에 올라간 뒤라 필요 없는 캐시). 적용 후 **재부팅 없이** 재시작 성공(시작 시 MemFree 4082 MB로 실패했던 때와 같은 조건).
**보조 수단**: `stop_all.sh --keep-worker` / `start_all.sh`가 떠 있는 워커를 재사용한다(ROS 쪽만 다시 켤 때). GUI·docker·mongodb를 끄면 약 0.45 GB가 더 생기지만 sudo가 필요하고 공용 기기라 하지 않았다.

## 32. D455가 영상을 한 장도 안 줌: 모든 요청이 503 (11/27 밤)

**증상**: 워커 `/health`는 `camera: true`인데 관측 노드가 10초마다 `HTTP Error 503`, 워커 로그 `no frame from the camera`. 관측 0회. 같은 날 앞선 실행에서는 415회 정상.

## 34. 지도 화면의 로봇 위치가 실제와 1.8 m 다름: AMCL에 통로 지도를 줌 (11/28 새벽)

## 36. 90도 회전이 안 됨: odom 방향이 또 멈춤 → 바퀴 odom을 직접 계산 (11/28 새벽)

**증상**: 조종기가 회전 때마다 "odometry frozen"으로 정지. 직진은 됨.
**확인**: 제자리 회전 명령에 바퀴는 좌 −2.17, 우 +2.17 rad(= 29°) 돌았는데 `/odom` 방향은 +0.0°. `use_imu: false`가 제대로 들어가 있었다. 28번과 같은 현상이 세 번째.
**원인**: TurtleBot3 드라이버(Foxy 바이너리)의 diff_drive_controller가 어느 순간 방향 갱신을 멈춘다. 코드를 볼 수 없어 원인은 모름. `/joint_states`의 바퀴 각도는 항상 맞았다.
**해결**: `robot/lib/wheel_odom.py`가 바퀴 각도로 `/odom`과 TF `odom → base_footprint`를 직접 만든다. launch 파일이 드라이버의 TF를 끄고(`publish_tf: false`) 드라이버의 토픽을 `/odom_tb3`로 옮긴다. 기본값(`OFB_WHEEL_ODOM=0`이면 드라이버). 확인: 회전 +28.4° / +57.2°(바퀴 계산 29° / 57°), 이후 주행 내내 정상.

## 37. 멈춰야만 기억하는 것이 부자연스러움 → 직진 중에도 기억 (11/28 새벽)

관측 노드가 "0.5초 이상 멈춰 있을 때만" 기록했다(`only_when_stopped`). 직진 중(0.12 m/s)에는 위치를 읽은 순간과 사진 사이 차이가 1~2 cm라 문제가 없고, 회전 중에는 사진이 번지고 각도 오차가 커진다. `OFB_OBSERVE_MOVING=1`(기본): 1초에 2번, 직진과 정지 중에 기록하고 회전 중(0.08 rad/s 이상, 끝나고 0.5초까지)만 건너뛴다.

## 38. 같은 컵이 기억 여러 개로 나뉨 (11/28 새벽)

**증상**: 같은 컵이 1 cm, 10~20 cm 간격으로 2~3개 기억됨. 한 사진에 "검출 2개"도 찍힘.
**원인**: (1) NanoOWL이 컵 몸통과 빨대까지 포함한 컵을 각각 상자로 냄. 두 상자의 IoU가 약 0.5라 기존 기준(0.7)으로는 둘 다 남음. (2) 관측 오차 설정(방향 1.7°, 거리 2 cm)이 실제 오차(AMCL 1~2°, 장착 오차)보다 작아, 다른 위치에서 본 같은 컵을 "다른 물체"로 판단.
**해결**: 상자 제거 기준 IoU 0.5 + 작은 상자의 80% 이상이 큰 상자 안이면 제거. `depth.yaml`: `maha_thresh 3.0 → 4.0`, `cos_thresh 0.80 → 0.75`, `sigma_bearing 0.03 → 0.06`, `sigma_range_a 0.02 → 0.05`.
**남은 문제**: 실습실 모니터가 "a laptop"으로 잡힘(노트북 기억 19개 중 대부분).

## 39. 터미널 명령을 복사하면 표의 선(│)이 같이 붙음 (11/28 새벽)

표 안의 긴 명령을 복사하자 세로선과 줄바꿈이 섞여 `bash: │: No such file or directory`. Jetson 홈에 짧은 명령을 만들었다: `./tele`(조종기), `./volt`(전압), `./mem`(메모리), `./nav`(이동 로그), `./ask`(글자 질문), `./reloc`(위치 다시 찾기). 노트북에서는 `ssh -t device06@192.168.1.206 ./tele` 한 줄.

## 40. 도착 후 좌우 확인 (11/28 새벽)

요청: 물체 앞에 도착하면 (+15° → 정지 → 원래 방향) 3번. `gridnav`의 `look_around`(1초씩 정지, 마지막엔 정확히 원래 방향). `OFB_NAV4_WIGGLE`(횟수, 기본 3, 0이면 끔), `OFB_NAV4_WIGGLE_DEG`(15). 그 뒤 찾기 노드가 재확인한다.
