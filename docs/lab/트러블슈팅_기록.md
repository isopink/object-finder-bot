## 1. 실습실 Wi-Fi에서 Claude Code 연결 실패

**증상**
- 노트북을 실습실 Wi-Fi(Jetson과 같은 네트워크)에 연결하면 Claude Code가 끊김.
- 터미널에서 실행하면 다음 오류가 남.
  ```
  API Error: Unable to connect to API: Self-signed certificate detected (SELF_SIGNED_CERT_IN_CHAIN)
  ```
- 학교 일반 Wi-Fi에서는 정상.

**원인 찾기**
1. 처음에는 실습실 Wi-Fi에 인터넷이 없다고 가정함. 그런데 11/18 로그에서 Jetson이 같은 네트워크에서 `apt`로 패키지를 받은 기록을 발견 → 인터넷은 되는 네트워크.
2. `Test-NetConnection <host> -Port 443`으로 github.com, claude.ai, api.anthropic.com 모두 **성공**.
   하지만 이 명령은 TCP 연결만 확인하고 인증서는 확인하지 않아서, 이 결과로는 원인을 가릴 수 없었음.
3. 오류 메시지가 가리키는 대로 인증서 발급자를 직접 확인.
   ```bash
   openssl s_client -connect api.anthropic.com:443 -servername api.anthropic.com -showcerts </dev/null \
     | grep -E "^ *[0-9] s:|i:"
   ```
   | 접속 대상 | 학교 일반 Wi-Fi | 실습실 Wi-Fi |
   |---|---|---|
   | api.anthropic.com | Google Trust Services (정상) | **학교 보안 장비(eWalker)가 발급** |
   | github.com | Sectigo (정상) | Sectigo (정상) |
4. 결론: 학교의 HTTPS 검사(SSL 인스펙션) 장비가 **Anthropic 쪽 통신만 골라서** 중간에서 인증서를 바꿔 끼움.
   Claude Code(Node.js)는 그 인증서를 모르므로 연결을 거부함. github는 검사 대상이 아니라 git은 영향이 없음.

**해결**
- 보안 장비의 **루트 인증서만** 파일로 저장. 처음 저장한 체인에는 api.anthropic.com용 위조 인증서도 섞여 있어서 루트 하나만 남김.
- 시스템 전체가 아니라 Node.js 프로그램만 이 인증서를 믿도록 설정.
  ```powershell
  setx NODE_EXTRA_CA_CERTS "$env:USERPROFILE\lab-ca.pem"
  ```
- 되돌리기: `setx NODE_EXTRA_CA_CERTS ""`

**배운 점**
- "포트 연결 성공"과 "통신 성공"은 다르다. TLS 문제는 `openssl s_client`로 인증서 체인을 직접 봐야 보인다.
- 정상 네트워크의 결과를 먼저 찍어 두면, 문제 네트워크의 결과와 바로 비교할 수 있다.
- 사설 인증서를 신뢰시키면 그 장비가 통신 내용을 볼 수 있다. 그래서 출처(학교 공식 장비인지)를 확인하고, 적용 범위를 Node.js로 좁혔다.
- 시행착오: 한 번은 학교 일반 Wi-Fi에 연결된 상태에서 테스트해 놓고 실습실 결과로 착각했다. 이후 테스트 스크립트 첫 줄에 **현재 SSID를 출력**하도록 했다.

## 2. 설정 후에도 Orca 안에서만 실패

**증상**
- 1번 설정 후, 새로 연 일반 PowerShell에서는 Claude Code가 접속됨.
- Orca(터미널 관리 앱)를 껐다 켜도 Orca 안에서는 계속 실패.

**원인 찾기**
- Orca 터미널 안에서 `$env:NODE_EXTRA_CA_CERTS`를 확인하니 **비어 있음**. 사용자 환경 변수에는 값이 있었음.
- Orca 프로세스 시작 시각을 보니, 창은 새로 떴지만 **백그라운드 데몬은 `setx` 이전부터 계속 실행 중**이었음.
- Orca 터미널은 데몬이 만들기 때문에 데몬의 예전 환경 변수를 물려받음.

**해결**
- Orca를 닫은 뒤 남은 프로세스까지 모두 종료하고 다시 실행.
  ```powershell
  Get-Process Orca -ErrorAction SilentlyContinue | Stop-Process -Force
  ```
- 재실행 후 Orca 안에서도 환경 변수가 보이고 실습실 Wi-Fi에서 Claude Code가 동작함.

**배운 점**
- Windows 환경 변수(`setx`)는 **새로 시작한 프로세스부터** 적용된다. 창을 다시 여는 것과 프로세스를 다시 시작하는 것은 다르다.
- "A에서는 되고 B에서는 안 된다"면 두 환경의 변수 값을 직접 출력해서 비교하는 것이 가장 빠르다.

## 3. 우회 시도: 아이폰 USB 테더링 (포기)

**시도한 이유**
1번의 원인을 찾기 전, 인터넷은 휴대폰으로 쓰고 Jetson 접속만 실습실 Wi-Fi로 하는 구성을 시도함.

**진행**
- 노트북이 아이폰을 정상 인식(`Apple iPhone`, `Apple Mobile Device Ethernet` 드라이버 OK)하는 것까지 확인. 케이블 문제가 아님.
- 테더링 어댑터가 계속 `Disconnected`. 요금제상 개인용 핫스팟을 쓸 수 없어서 중단.

**배운 점**
- 우회책보다 원인을 먼저 찾는 게 나았다. 원인(1번)을 알고 나니 테더링 자체가 필요 없었다.
- 필요하면 쓸 수 있는 대안: USB Wi-Fi 동글로 두 네트워크에 동시 연결하고, 인터페이스 우선순위(`InterfaceMetric`)로 경로를 나누는 방법.

## 4. NetClient5 설치 중 드라이버 차단 경고

**증상**
학교 PC 관리 프로그램(NetClient5)을 설치하는 중 Windows 경고가 뜸.
```
이 장치에 드라이버를 로드할 수 없습니다. 드라이버: cpuz139_x64.sys
보안 설정에서 이 드라이버를 취약한 드라이버로 감지하여 로드하지 못하도록 차단하고 있습니다.
```

**원인 찾기**
- 다운로드 폴더와 실행 중인 프로세스로 어느 설치 파일이 원인인지 확인 (NetClient5).
- 막힌 건 하드웨어 정보 수집용 구버전 CPU-Z 드라이버. Windows 11의 "취약한 드라이버 차단 목록"에 올라 있음.
- 설치 로그를 보니 에이전트 서비스는 실행 중이고 학교 서버로 상태 보고도 성공.

**해결**
- 경고만 닫음. 보안 설정(메모리 무결성 / 취약한 드라이버 차단)은 **끄지 않음**.
- 프로그램의 핵심 기능은 정상 동작. 하드웨어 사양 보고만 빠짐.

**배운 점**
- 경고 창이 떴다고 설치가 실패한 것은 아니다. 실제로 무엇이 막혔는지(로그, 서비스 상태)를 확인하고 판단한다.
- 보안 기능을 끄는 것은 마지막 수단이다.

## 5. 실습실 Wi-Fi에서 Jetson SSH 응답 없음

**증상**
- 노트북은 실습실 네트워크에 정상 연결(`192.168.1.x`, 게이트웨이 `192.168.1.1`).
- `ssh` 설정의 Jetson 주소(`192.168.1.206`) 22번 포트가 응답 없음.
  ```
  ssh: connect to host 192.168.1.206 port 22: Connection timed out
  ```

**확인한 것**
- 학교 일반 Wi-Fi에서 같은 주소로 접속하면 TCP는 열리는데 SSH 응답이 없음 → 다른 네트워크의 다른 장비. 그 Wi-Fi로는 Jetson에 닿지 않음.

- 실습실 네트워크 전체(`192.168.1.2~254`)에서 22번 포트가 열린 기기를 찾았는데 **하나도 없음** → IP가 바뀐 게 아니라 Jetson이 네트워크에 없음.

**원인**
두 가지가 겹쳐 있었음.
1. **Jetson이 꺼져 있었음.** ASUS PE1000N은 처음 써 보는 장비라 전원 켜는 법부터 찾아야 했음. 같은 계열(PE100A, PE400D) 설명서를 보고 앞면 전원 버튼을 찾아 켬.
2. **노트북 Wi-Fi가 몰래 바뀌어 있었음.** 다시 스캔하자 254개 주소가 **전부** 열린 것으로 나옴. 이상해서 네트워크를 확인하니 Windows가 학교 일반 Wi-Fi로 자동으로 옮겨 가 있었음. 그 네트워크의 보안 장비가 모든 연결에 대신 응답해서, 열린 것처럼 보인 것.

**해결**
- 실습실 Wi-Fi에 다시 연결하고, 학교 일반 Wi-Fi의 "자동으로 연결"을 해제.
- Jetson이 켜진 뒤 `ssh` 접속 성공 (비밀번호 요구 = SSH 서버 응답).
- 이후 매번 비밀번호를 치지 않도록 SSH 키(ed25519)를 만들어 Jetson `~/.ssh/authorized_keys`에 등록.
  ```powershell
  ssh-keygen -t ed25519 -f "$env:USERPROFILE\.ssh\id_ed25519"
  type "$env:USERPROFILE\.ssh\id_ed25519.pub" | ssh device06@<jetson-ip> "mkdir -p ~/.ssh && chmod 700 ~/.ssh && cat >> ~/.ssh/authorized_keys && chmod 600 ~/.ssh/authorized_keys"
  ```
- `sudo`는 여전히 비밀번호가 필요하므로 udev 규칙 설치처럼 `sudo`가 필요한 명령은 직접 터미널에서 실행.

**배운 점**
- "전부 열림"은 "전부 닫힘"만큼 이상한 결과다. 결과가 너무 좋으면 측정 환경(지금 어느 네트워크인지)부터 의심한다. 1번의 교훈(테스트 전에 SSID 확인)을 여기서도 지켰어야 했다.
- 포트 스캔으로 "열림"이 나와도, 실제로 `ssh`를 붙여서 배너가 오는지 확인해야 진짜 SSH 서버다.
- 원격 장비 문제를 볼 때는 **전원 → 네트워크 → 서비스** 순서로 아래층부터 확인한다.

## 6. D455용 librealsense 빌드 실패 (cmake 2번)

**증상**
`./robot/install_realsense_jetson.sh`가 시작 1분 만에 `[FAIL] cmake failed`로 끝남. 고친 뒤 다시 돌리자 다른 오류로 또 실패.

**원인 찾기 1: CMake 버전**
```
Compatibility with CMake < 3.5 has been removed from CMake.
```
- 시스템 cmake는 3.16인데 오류는 CMake 4.x의 메시지. `which -a cmake`로는 시스템 것만 보였음.
- 스크립트는 conda 환경을 켠 뒤 cmake를 부름 → conda 환경 안을 보니 **pip로 설치된 CMake 4.4**가 있었음. 이 버전이 librealsense의 오래된 설정을 거부.
- 해결: 스크립트가 `/usr/bin/cmake`를 직접 쓰도록 수정.

**원인 찾기 2: Python을 못 찾음**
```
Could NOT find Python (missing: Python_INCLUDE_DIRS Development) (found version "2.7.18")
```
- conda Python(3.8)을 넘겼는데 cmake는 시스템 Python 2.7을 찾고 있었음.
- 스크립트는 `PYTHON_EXECUTABLE`(옛 방식)만 넘기는데, librealsense는 새 방식(`FindPython`)을 써서 `Python_EXECUTABLE`(대소문자가 다름)을 읽음.
- 해결: `-DPython_EXECUTABLE`도 넘기도록 수정. 스크립트 전체를 다시 돌리기 전에 cmake만 따로 실행해 통과를 확인.

**덤: 빌드 폴더 오염**
도중에 Jetson이 꺼지면서(7번) cmake가 받다 만 파일이 남아 `nlohmann_json` 업데이트 오류가 남. 빌드 폴더를 지우고 다시 실행해서 해결.

**설치 단계에서 2번 더**
- `sudo make install`이 conda 환경 안에 `pyrealsense2` 폴더를 **root 소유로** 만들어서, 스크립트가 그 안에 모듈을 복사하지 못함(`Permission denied`). → 폴더가 root 소유면 소유권을 가져오도록 수정.
- 다시 돌렸더니 이번에는 `[OK] all checks passed`가 나왔는데 실제로는 설치가 안 된 상태였음. 폴더에 보조 파일만 있어도 `import pyrealsense2`가 성공해서(빈 namespace 패키지), 스크립트가 "이미 설치됨"으로 판단하고 복사를 건너뜀. 버전이 `?`로 나온 게 단서. → `rs.context`까지 있는지 확인하도록 수정.

**속도**
Jetson 전원 모드가 `MODE_15W_2CORE`(코어 2개)였음. `sudo nvpmodel -m 8`(20 W, 6코어)로 바꾼 뒤 `make -j6`.

**배운 점**
- 오류 메시지가 가리키는 버전과 실제로 설치된 버전이 다르면 **PATH**를 의심한다. 가상환경(conda)을 켜면 같은 이름의 다른 프로그램이 앞에 온다.
- CMake 변수는 대소문자를 구분한다. `PYTHON_EXECUTABLE`과 `Python_EXECUTABLE`은 다른 변수다.
- 긴 빌드 스크립트를 처음부터 다시 돌리기 전에, 실패한 단계만 손으로 재현해서 고쳐졌는지 먼저 확인하면 시간을 아낀다.
- `sudo`로 만든 파일은 root 소유가 된다. 일반 사용자 폴더(conda 환경) 안에서 `sudo make install`을 하면 권한이 섞인다.
- "OK"가 나와도 검사가 무엇을 확인했는지 봐야 한다. import 성공은 모듈이 **쓸 수 있다**는 뜻이 아니다.

## 7. 작업 중 Jetson이 갑자기 꺼짐 + 노트북 Wi-Fi 다시 바뀜

**증상**
cmake 시험 중에 SSH가 끊김. 노트북은 학교 Wi-Fi로 또 넘어가 있었고, 실습실 Wi-Fi로 돌아온 뒤에도 Jetson이 응답하지 않음.

**원인**
- 노트북: 학교 Wi-Fi 자동 연결이 아직 켜져 있었음. `netsh wlan set profileparameter name="<학교 Wi-Fi>" connectionmode=manual`로 꺼서 해결.
- Jetson: 다시 접속해 보니 켜진 지 2분. `last -x` 기록에 이전 세션이 `crash`로 남음 → 정상 종료가 아니라 **전원이 끊긴 것**. 로봇 배터리를 연결하는 동안 전원 선이나 USB 선이 건드려진 것으로 추정. USB 장치(OpenCR, LiDAR, 카메라)도 함께 빠져 있었음.

**배운 점**
- 원격 장비가 사라지면 `uptime`과 `last -x`로 "재부팅됐는지, 정상 종료였는지"부터 본다.
- 로봇 위 전원 선과 USB 선은 케이블타이로 고정한다. 작업 중에 건드리면 재부팅과 장치 재연결이 함께 일어난다.
- `nvpmodel` 설정은 재부팅 후에도 유지된다.

## 8. 로봇 배터리 0.05 V, 충전 안 됨 (진행 중)

**증상**
bringup은 성공(`Run!`)하는데 `/battery_state` 전압이 0.05 V. 11/18과 같은 증상.

**원인 찾기**
- OpenCR는 Jetson USB 전원만으로도 켜지기 때문에 bringup은 배터리 없이도 성공한다. "bringup 성공 = 전원 정상"이 아님.
- LiDAR가 빠져 bringup이 거부될 때는 OpenCR 노드(`turtlebot3_ros`)만 따로 띄워 전압을 읽었음.
- 배터리는 충전기에 꽂혀 있는 상태였음 → 로봇에는 배터리가 없는 상태라 0 V가 정상.

- 충전기에 꽂자 **빨간불이 깜빡임**. 충전기 라벨: "red flash = output short-circuit or wrong polarity".
- 극성과 연결을 확인하고 **다른 충전기로 바꿔도 같은 증상** → 충전기 문제가 아니라 배터리 쪽.
- 11/18에도 로봇에 꽂은 상태로 0.07 V였음 → **과방전**으로 배터리 전압이 0 V 근처라 충전기가 단락으로 판단한 것으로 추정. 배터리 커넥터나 선의 단락일 가능성도 남아 있음.

**판단**
과방전된 Li-Po를 억지로 충전하면 부풀거나 불이 날 수 있음. 직접 살리지 않고 조교님께 교체를 요청하기로 함.

**배운 점**
- 같은 증상이 장비를 바꿔도 반복되면, 바꾸지 않은 쪽이 원인이다 (충전기 2대 → 배터리).
- Li-Po는 다 쓴 뒤 방치하면 과방전으로 못 쓰게 된다. 실습이 끝나면 배터리를 분리하고, 다음 실습 전에 충전해 둔다.
